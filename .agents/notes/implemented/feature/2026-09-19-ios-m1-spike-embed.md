# iOS M1 spike embed: quickjs host in a minimal simulator app

Status: implemented

Date: 2026-09-19
Class: feature
Task: T-0003

## Problem

M1's core spike (runtime/spike) had a proof run on the macOS CLI only. The
iOS plane had no evidence that the platform-neutral C host
(dsh_spike_host.c) embeds and passes the m1.spike.boot E2E scenario on an
iOS simulator: no Xcode project, no story for how the JS bundle reaches a
sandboxed app, and no canonical log lines captured from iOS.

## Decision

hosts/ios now contains a minimal UIKit app (`DSHSpike`, bundle id
`org.dsh.DSHSpike`) that links `runtime/spike/host/dsh_spike_host.c` plus
the four vendored quickjs-ng C files (materialized by
`runtime/spike/vendor/ensure.sh` first) and drives the scenario from a
dedicated serial DispatchQueue: the whole JS lifetime
(new → eval → pump → free) executes inside one block on one thread, and the
sink callback prints each canonical `dsh.spike.log:` line to stdout AND
NSLog, so both channels carry byte-identical lines (the shared checker
passes 9/9 on either). The verdict (PASS/FAIL + engine version) is shown in
the app UI.

The JS bundle (logger.js, the scenario, the vendored util-crypto package)
is compiled into the binary as NUL-terminated byte arrays — generated by
`Tools/gen_bundle_header.py` from `../../runtime/spike` sources, committed
under `App/Generated/` — and staged at launch into
`NSTemporaryDirectory()/spike/` preserving the runtime/spike layout; that
directory is the `bundle_root` the C loader resolves imports against.

The Xcode project is generated with XcodeGen (`project.yml` + `gen.sh`);
the generated `DSHSpike.xcodeproj` is ALSO committed so CI and fresh clones
build without xcodegen. The project's pre-build phase re-runs the generator
whenever a runtime/spike JS input changes, keeping the embedded bundle
byte-identical to the checkout. `dev-ios.yml` now does the real xcodebuild
(generic iOS Simulator destination, unconditional) plus a best-effort
simulator run + checker step (continue-on-error for the emulator stage
only, justified in-line). Evidence: scenario m1.spike.boot on simulator
dsh-iphone (iOS 26.5) — PASS 9/9, committed under
`hosts/ios/artifacts/m1-spike/`.

## Alternatives considered

- Bundle the JS as app resources (flat names) and map them at launch:
  rejected — flat resource naming (`index.js`) is fragile, and byte
  provenance of what runs becomes a bundle-copy phase question instead of a
  compiled-in constant.
- Point `bundle_root` directly into the read-only `.app` bundle via a
  folder reference: rejected — a folder reference copies the whole
  directory verbatim, so excluding the untracked quickjs vendor tree (and
  other non-bundle files) is not expressible; the app would carry engine
  sources as dead weight.
- Commit only project.yml and generate the project in CI: rejected for this
  spike — it adds a brew dependency and a generation step to every CI run;
  the committed project is regenerable via `gen.sh` and the pre-build phase
  keeps the embedded bundle fresh. Revisit if project.yml/pbxproj drift
  becomes a real problem.
- Capture via `simctl launch --console-pty`: rejected — console-pty merges
  stdout and stderr, so each canonical line would appear twice (stdout copy
  + NSLog copy) and the one-to-one checker would count 18 records; the run
  captures stdout and stderr to separate files instead
  (`simctl launch --stdout=… --stderr=…`).

## Consequences

- The spike app is stateless between launches; relaunching re-runs the
  scenario (idempotent, fresh UUID per run).
- `exitStatus` in receipt.json means "run completed without crash or abort"
  (0) — a GUI app has no process exit code.
- The committed pbxproj + project.yml pair can drift; gen.sh regenerates,
  and the pre-build phase keeps the JS bundle itself self-healing.
