## 问题陈述（不含解决方案）

运行时是单线程协程宿主：JS 跑在一条串行队列上，宿主回调派发到该队列
（D2/D8），而**系统中没有任何东西能调度一次未来的回调**。这是 v0 的刻意边界，
而它的代价现在可以度量了：

1. **上游包把定时器当作环境全局来调用。** `@deepseek-ai/dsh-timeout`（deadline
   保险丝、异步迭代器的空闲看门狗）以及经它传导的 agent loop 直接调用裸的
   `setTimeout`/`clearTimeout`。在我们的宿主上这些名字不存在：所有武装保险丝的
   代码路径都抛 `ReferenceError: setTimeout is not defined`，所有与这类保险丝
   竞速的 `await` 要么失败、要么永不确定（套件中两个挂起类条目）。
2. **定时器表面是*能力*而非 polyfill。** 定时器在当前回合之后触发 —— 在本架构
   上这只能意味着宿主在宿主选定的时间重新进入运行时队列。这恰恰是网关存在的
   意义：一个异步的、带权限旗标、有审计、派发到串行队列的原语。把它当作
   `globalThis.setTimeout` 灌进去会绕过协商与审计，而且日后不可移除（全局量在
   出厂当天就是冻结形状）。
3. **shim 层已经在乞求它。** `node:timers/promises` 是一个其函数全部抛出
   "no timer seam in the spike runtime" 的占位。契约层面的接缝才是让该 shim
   （且只有它）在与其他一切相同的协商背后长出真实行为的东西。

## 提案必须遵守的设计约束

- **D2（运行时上无线程）**：定时器在宿主侧触发；回调像所有其他宿主事件一样
  *投递*到串行队列。定时器绝不在第二条线程上跑 JS。
- **D8（事件驱动）**：定时器是事件源，不是阻塞睡眠。
- **契约先行（D5）**：表行冻结之前任何宿主不得落地；shim 层不得在网关之外
  发明宿主回调。
- **增量 minor（§8）**：没有该接缝的宿主继续按 `gateway@1` 协商并对两行回答
  `unavailable`，与 `wasmRun`/`ishRun` 完全一致。

## 提议的形状（两行，一个旗标）

### `timerSchedule(delayMs, opts?) → { timerId }` —— 调度一次唤醒

- `delayMs`：≥ 0 的整数，**由宿主设上限**（dsh-timeout 自身按 `MAX_TIMER_DELAY_MS`
  钳制；宿主可以更紧并在拒绝的 `reason` 中说明，绝不静默截断 —— 规则 5）。
- `opts.tag`（可选）：调用方自选的审计标签。审计链必须能回答"哪个插件武装了
  哪些定时器"。
- 在定时器**已武装**时决议，而非触发时。请求/响应不携带回调 —— 唤醒走
  **事件通道**投递（§ 事件通道）：`timer.fire { timerId, tag }`。
- `timerId` 是不透明整数；宿主只保证在存活定时器之间唯一（取消后复用合法且
  可审计）。

### `timerCancel(timerId) → { cancelled: boolean }` —— 解除一次唤醒

- 未知或已触发的定时器返回 `cancelled: false`（幂等；触发与取消的竞态二选一
  收场，绝不双发 —— 宿主选其一，审计记录选了哪个）。

### 事件通道：`timer.fire`

`timer.fire { timerId, tag }` 投递到调用方的串行队列。一次武装 ⇒ 至多一次触发
（v1 不做 interval —— 供应商化闭包中没有不能用"重新武装"循环表达的
`setInterval` 语义，无状态重武装保持原语最小；有证据再议）。

### 权限旗标：`timer`

一个旗标同时约束两行。理由：只许武装不许取消是脚枪（套件的看门狗测试恰恰在
测取消），拆开会催生半能力宿主，而协商数据无法有效区分它们。

### 本提案 v1 刻意不包含的

- **不做 `Date.now()` 替代** —— 只做单调调度；壁钟需求（locale、ttl 展示）不是
  定时保险丝，若有一天成为网关工作应另有归属。
- **不做全局 `setTimeout`。** 从 `setTimeout` 形状代码到这些原语的映射住在
  *shim 层*（`node:timers`、`node:timers/promises`、spike 自己的接缝），它协商
  旗标并在缺席时响亮失败。全局量会成为同一能力的第二个不受治表面 ——
  RFC 0002 的教训的缩影。
- **不做漂移/对齐保证。** 宿主"不早于 `delayMs`"触发，除自身审计链外不做上限
  承诺；需要精确计时的测试继续留在 fake timers（排除类）。

## 为什么是原语而不是插件

特权层按构造拥有跨回合状态。在武装与触发之间存活下来的定时器定义上就是宿主
状态（运行时可能在两刻之间被拆除），所以它不能由插件供给；而 notify 原语已经
确立"稍后唤醒我"是宿主的工作。唯一新的治理问题是*哪一个稍后*，这正是这两行
所冻结的。

## 合规性草案（供本提案毕业时并入 §7 表）

1. 协商 `timer` → `timerSchedule(50)` 武装；该 id 的一次 `timer.fire` 到达
   串行队列；与队列排空的顺序是：触发在当前任务完成*之后*投递（绝不重入）。
2. 对已武装的 id 调 `timerCancel` 抑制触发；对已触发的 id 返回
   `{ cancelled: false }`。
3. 未审计的 `timerSchedule` 与任何未记录调用一样不通过审计门。
4. 无该接缝的宿主对两行都回答 `unavailable`，且永不发出 `timer.fire`。

## 考虑过的替代方案

- **在 spike 运行时里 polyfill 一个全局 `setTimeout`。** 否决：无协商、无审计、
  无权限门，而且上游代码一旦依赖其怪癖，全局表面永远收不回。
- **用空通知把定时器表达成 `notify`。** 否决：notify 调度的是*用户可见*通知
  （权限弹窗、系统设置）；把不可见唤醒搭在它上面污染权限叙事和真机上的通知
  中心。
- **什么都不做（继续排除依赖定时器的 spec）。** 否决为终态：该排除类是上游
  套件清单里最大的一桶（100+ spec），而且它遮住的是真实产品表面（agent loop
  的 abort 保险丝），不是证明它。
- **单一 `sleep()` 原语返回 Promise。** 否决：只有 promise 的睡眠无法表达
  "武装看门狗、步骤完成则取消"，除非每次武装分配一个 promise；套件的挂起类
  失败恰恰是缺失取消的情形。此外，只有 promise 会迫使 shim 合成 id，把宿主
  已有的状态再加回去。
