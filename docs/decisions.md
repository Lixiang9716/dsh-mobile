# Decisions

The project's decision log: one entry per settled decision, numbered D0,
D1, … contiguously. Allocate numbers with `gov decision next` (it checks
the branch base for collisions), append with `gov decision add`, and
never renumber or reuse a row — decisions are addresses, not prose.

Every entry records what the decision BEAT under its Alternatives
heading; a decision without its alternatives invites re-litigation,
which is the exact failure this log exists to prevent.
`gov decision verify` checks numbering, the alternatives record, and
orphaned references; `gov recall` searches these entries.

## D0 — Adopt the govrail governance plane

- **Decision**: gates + notes + receipts as the working discipline
- **Alternatives**: prose-only agent rules (not checkable); ad-hoc conventions (drift silently)

## D1 — quickjs-ng as the mobile JS engine

- **Decision**: quickjs-ng (pure-C interpreter) carries the Harness core; nodejs-mobile rejected
- **Alternatives**: nodejs-mobile (V8: an order of magnitude more memory, JIT gray zones, no multi-runtime isolation)

## D2 — single-threaded coroutines replace subprocesses

- **Decision**: tool execution re-implemented in-process as coroutines behind `ctx.subprocess`
- **Alternatives**: requiring real subprocesses (physically refused on iOS); worker threads (defeats single-runtime auditability)

## D3 — UI is a Web Client plugin rendered in WKWebView

- **Decision**: official React UI is the default Web Client plugin; mobile-ui is another
- **Alternatives**: native-only UI (loses the official frontend and slot ecosystem); React Native rewrite (heavy, diverges from upstream web)

## D4 — distribution outside the App Store

- **Decision**: open-source, self-signed/TrollStore/EU channels
- **Alternatives**: App Store (guideline 2.5.2 bans downloaded code — a plugin ecosystem cannot pass); TestFlight (same review)

## D5 — contract first

- **Decision**: `contract/` (primitives + data protocols) frozen before any implementation
- **Alternatives**: code-first, freeze later (AI-era rework cost; four platforms drift before the地基 exists)

## D6 — pinned upstream + outboard implementation packages

- **Decision**: upstream DSH pinned (manifest), adaptations live in `system-plugins/`, never in vendored edits — same discipline applied to govrail itself in CI
- **Alternatives**: tracking upstream main (lineage breakage at 0.1.x velocity); wholesale fork (permanent merge debt)

## D7 — checkpoint as roaming

- **Decision**: checkpoint format shared across hosts; background suspension becomes cross-device handoff
- **Alternatives**: demanding background residency (physically refused by iOS); no persistence (tasks die at lock screen)

## D8 — all modules event-driven, including streaming

- **Decision**: inter-module communication is events or explicit async interfaces; LLM token streams are event pipelines; checkpoint = event queue drained
- **Alternatives**: direct module calls + blocking whole-result APIs (couples components, kills substitutability); polling (wasted battery, races)

## D9 — Port upstream DSH packages as verbatim plugins; never reimplement Harness behavior in-house

- **Decision**: product-carrying upstream packages (agent-loop, session, session-projection, llm, settings, cordis runners) are vendored VERBATIM (pinned tarball + sha256 + PROVENANCE, the ensure.sh pattern) and driven through adapter plugins: system plugins implement the upstream service contracts (fs / subprocess Service / ui) over the 9 gateway primitives, a transport seam maps upstream fetch onto httpFetch, and the runtime boot constructs the upstream runner with those services. In-house code is glue only (shims, adapters, scenarios) — never product behavior.

## Alternatives

- In-house reimplementation of the Harness flow on QuickJS (what the first overnight iteration drifted into: a self-authored mini agent-loop + mock LLM + in-house session flow): rejected — forks product behavior from upstream, guarantees divergence at 0.1.x velocity, and contributes none of the mobile constraints back to the ecosystem; the host would own a second Brain.
- Full nodejs-mobile to run upstream unshimmed: rejected — D1 already beat it (memory footprint an order of magnitude higher, JIT gray zones, no multi-runtime isolation); the shim surface is small and measured (ARCHITECTURE.md §3).
- Pin-and-fork upstream (vendor once, edit locally): rejected — D6's lineage discipline; verbatim + shims keeps re-pins cheap and upstream improvements flowing.

## D10 — Release-please drives the version stream

- **Decision**: one repository-wide semver version, derived from the conventional commits the `commit-format` gate already enforces. release-please keeps a standing release PR that bumps `version.txt`, writes `CHANGELOG.md` and syncs the three host manifests through `extra-files` (XML+xpath for `Info.plist`, the generic annotation for `build.gradle.kts`, JSON+jsonpath for `app.json5`); merging it tags `vX.Y.Z` and `release/packages` attaches the three host builds to that Release. The bot PR needs `RELEASE_PLEASE_TOKEN` (PAT or GitHub App token) because events created by `GITHUB_TOKEN` do not trigger workflows, so a `GITHUB_TOKEN` release PR would never receive the `gates` check that `main` requires.
- **Alternatives**:
  - Per-host version streams (three independent numbers): rejected — the three hosts ship together in ONE `release.yml` run, so three numbers mean three PRs and three changelogs for one build set; the drift already present (iOS `0.1.0` / Android `0.1.0-spike` / HarmonyOS `1.0.0`) is the manual alternative failing in place.
  - Hand-maintained versions plus `gh release create`: rejected — rule 1's standard is that a promise a command can check is a gate; a hand-cut release reintroduces exactly the drift the `commit-format` gate was adopted to prevent, and nothing would catch a forgotten host bump.
  - `skip-github-pull-request: true` (a PAT-free tagging mode): rejected — it tags HEAD without ever moving the version files, so the version source of truth does not advance and the next run computes the same tag again.
  - Admin-bypass merging of a `GITHUB_TOKEN` release PR: rejected as the default — it makes the bypass routine, contradicting AGENTS.md's "reserved for deliberate direct landings, not a default".

## D11 — Release-please authenticates with GITHUB_TOKEN; the repository must permit it to open PRs

- **Decision**: **CORRECTED BY D13** — the dispatched check described below does NOT satisfy branch protection for a pull request; verified on PR #111, which stayed `BLOCKED` with a green `gates` check on its exact head SHA. Reaching release PRs still needs a user-attributed token, as D10 said. What stands here: the PAT is no longer read, and the package path needs no credential. supersedes D10's `RELEASE_PLEASE_TOKEN` clause. release-please runs with `secrets.GITHUB_TOKEN`, and the required repository setting **"Allow GitHub Actions to create and approve pull requests"** (`can_approve_pull_request_reviews`) is ON — without it `POST /pulls` is refused outright with *"GitHub Actions is not permitted to create or approve pull requests"*, which is the failure the PAT had been masking. **That setting plus one explicit dispatch is the whole mechanism, and both halves are load-bearing.** The setting lets `GITHUB_TOKEN` open the PR; the dispatch supplies the check. The suppression rule that D10 reasoned about is real but *partial*, and the measurement is what settles it: on PR #107 the release PR's **first** creation did start its `pull_request` workflows (`gov` plus all three platform pipelines, all green, PR `CLEAN`), while a later **branch update** from an ordinary `push: main` run produced a suppressed run (`action_required`) and **no checks at all** — PR `BLOCKED`. The release branch is rewritten on every push to `main`, so the PR event cannot be the source of the required check. `workflow_dispatch` is a documented exception to the suppression, so the last step of `release/version` **dispatches the `gov` workflow at the release branch** (`.github/workflows/gov.yml` gains `workflow_dispatch`; the step runs `gh workflow run gov.yml --ref <release-branch>` and fails loud if refused). Its `gates` check lands on the same commit `main` protection asks about — a real gate run on the real commit, never a check fabricated through the Checks API. The `RELEASE_PLEASE_TOKEN` secret is no longer read by any workflow; it is left in place, unread. The release pipeline's workflows are named by stage and host (`release/version` prepares; `release/ios`, `release/android`, `release/harmony` package), mirroring `dev/ios`, `dev/android`, `dev/harmonyos`.
- **Alternatives**:
  - Keep the fine-grained PAT (`RELEASE_PLEASE_TOKEN`) and add `pull requests: write`: rejected — it makes the pipeline depend on a credential that fails in a way nothing local can detect. The failure it produced is instructive: the PAT authenticated, carried `contents: write`, let the action create its branch and commit, and died only at its final `POST /pulls`, so the version stream was dead for days while every visible signal looked healthy. A credential the workflow does not need cannot be misconfigured, and the repository setting it was masking is discoverable and named by the error it produces.
  - `GITHUB_TOKEN` plus admin-bypass merging: rejected by D10 already, and still rejected — it makes the bypass the routine path for every release.
  - `skip-github-pull-request: true`: rejected by D10 already, and still rejected — it tags HEAD without moving the version files, so the version source of truth does not advance.
  - Rely on the `pull_request` event alone and drop the dispatch: rejected on measurement, not on caution — the PR's first creation did get its checks from the PR event, but a branch update from an ordinary push to `main` produced `action_required` and no checks, so the required `gates` check would be absent exactly when the PR is current. The dispatch costs one ~20s run and is the only path whose behaviour does not depend on suppression semantics.
  - Put the PAT into a step output and pass it to the action, falling back to `GITHUB_TOKEN` when it cannot open pull requests: rejected — two credential paths whose PAT branch cannot be exercised from here, so half of it would ship untested.
  - Dispatch by check-run API instead of running the gates: rejected outright — a green check that did not run the gates is exactly the vacuous-check failure rules.md rule 6 exists to prevent.

## D12 — The release is triggered by the tag push, and the bot stops at the release PR

- **Decision**: (The release PR's own required check is D13's subject, not this entry's — the package path below never used it.) supersedes D10's and D11's assumption that merging the release PR cuts the release. The three package workflows (`release/ios`, `release/android`, `release/harmony`) are triggered by **a `v*` tag push** — `git push origin vX.Y.Z` — and by nothing else automatic. `release/version` keeps only the half of release-please that computes rather than publishes: `skip-github-release: true` makes it stop at the release PR, so it never tags and never publishes; merging that PR advances `version.txt`, `CHANGELOG.md` and the three host manifests on `main`, and the human's tag push is what builds. Each package workflow **creates the Release for its tag when none exists** (`gh release create --verify-tag`, racing three hosts safely), then attaches its package. The `release: published` event is deliberately **not** a trigger: the workflows now create Releases themselves, so listening to that event would fire a second build of the same tag. `tools/release/check-tag-version.sh` runs first in every package workflow and refuses a tag that disagrees with any of the four version files, naming every mismatch at once. Cutting a release now needs only `contents: write` — none of the PR permissions, PATs or suppression semantics the package path never used.
- **Alternatives**:
  - Keep the release cut by release-please and triggered by `release: published`: rejected — it couples the release to the bot completing, which is the exact failure mode this pipeline spent days in. A token that could not open a pull request, a repository setting that forbade it, an event suppressed for `GITHUB_TOKEN`: each one stopped the release at a step that reported nothing, and each was invisible from the repository. A tag is a gesture a human makes deliberately and can retry, and the package path is the part with no moving credential.
  - Keep `release: published` **as well**, so publishing a Release by hand still builds: rejected — the package workflows now create the Release on a tag push, so that event would fire again for the same tag and build everything twice. Two triggers for one logical release is a race, not a convenience.
  - Dedupe the two triggers with a `concurrency` group keyed on the tag: rejected — it makes correctness depend on cancellation semantics to paper over there being two sources of truth for "a release happened". Better to have one trigger.
  - Have the human maintain the version files and tag by hand (release-please removed entirely): rejected by D10 already, and still rejected, but the reason is what shapes this decision — a hand-cut release reintroduces exactly the drift the `commit-format` gate exists to prevent. So the bot keeps the mechanical half (version computation and changelog, reviewed in a PR) and `check-tag-version.sh` enforces that the human's tag agrees with it. The trigger moves to the human; the bookkeeping does not.
  - Trigger on tag push with no version guard: rejected — a human-chosen tag with machine-written version files is precisely the drift this design could introduce, and it would be silent: the app installs fine under the wrong number and nothing downstream compares the two. The guard is the price of moving the trigger, and it fails before anything builds.

## D13 — The release PR's required check must come from its own events; a dispatched run does not satisfy it

- **Decision**: corrects D11's central claim and D12's inherited one. Verified on PR #111 with the check present and green: a check run produced by a **`workflow_dispatch`** run does **not** satisfy branch protection's required check for a pull request, even when it lands on the PR's exact head SHA with the required context (`gates`) and app (`15368`) and its check suite is linked to the PR. The PR stayed `BLOCKED` with an empty check rollup for 12+ minutes with nothing else to block it: `main` requires only `gates`, `strict: false`, 0 required reviews, `enforce_admins: false`, and the head commit carried `gates = success` while the test-merge commit carried no checks at all. When the PR's own `pull_request` runs were **not** suppressed (PR #107's first creation), the same PR reached `CLEAN` — so the check is accepted only when it comes from the pull request's own event flow. **D10's original PAT rationale was therefore correct** and D11's dismissal of it was wrong: GITHUB_TOKEN-created events are suppressed, so a release PR opened with GITHUB_TOKEN cannot receive the check that `main` requires, and producing that check by dispatch is not a substitute. What remains true from D11 is that the PAT is not read by any workflow and that the *package* path needs no credential: with D12, `git push origin vX.Y.Z` cuts the release and needs only `contents: write`. What is now open is narrow and named — **who authors the version-bump commit**: a release PR from release-please (needs a user-attributed token, i.e. a PAT or App token, as D10 said) or a normal human/agent PR (gets normal checks, no credential at all, and `tools/release/check-tag-version.sh` keeps it honest). The second is the recommendation; it is the owner's call because it retires a component D10 chose.
- **Alternatives**:
  - Keep the dispatch and declare the release PR mergeable-with-bypass: rejected — it makes the bypass the routine path for every release, which is what D10 refused and what AGENTS.md says the bypass is not for. A bypass that is always taken is not a gate.
  - Rely on the dispatch and treat the earlier `CLEAN` as proof: rejected — that `CLEAN` came from the PR's own `pull_request` runs, which only fired because the release PR happened to be *created* by a `workflow_dispatch`-triggered release-please run. On the normal path — a `push: main` run — all four `pull_request` runs arrived as `action_required`, and the dispatched check did not rescue the PR. One observation of one moment was mistaken for the mechanism twice; this entry records the measurement that settles it.
  - Restore the fine-grained PAT as the only answer: rejected as the *default*, though it is now a legitimate option — it is what D10 prescribed and it works, but it needs the owner's web-UI action for a permission, and it re-introduces the credential class of failure this pipeline spent days in. A human-authored bump PR reaches the same end state with no credential, which is why it is the recommendation rather than the fallback.
  - Add `merge_group` / a merge queue to sidestep the check: rejected — it changes the merge model of the whole repository to work around one PR's provenance.

## D14 — The version bump is an ordinary pull request; release-please is retired

- **Decision**: supersedes D10 (release-please drives the version stream) and completes D13. The version-bump commit is authored by a person or an agent on a normal branch: `tools/release/bump-version.py X.Y.Z` rewrites `version.txt`, the iOS `Info.plist` `CFBundleShortVersionString`, the Android `versionName` and the HarmonyOS `versionName`, and prepends the release's `CHANGELOG.md` section built from the conventional commits since the last tag. It prints the version those commits imply as a hint (a `feat` or a breaking change bumps the minor pre-1.0, a `fix` the patch) and lets a person decide; it refuses a partially-applied bump before writing anything, and re-reads every file it writes. The pull request that carries it is ordinary, so it receives the required `gates` check the ordinary way — which is the entire reason the bump is a normal PR (D13). `release-please` is removed: its workflow, `release-please-config.json`, `.release-please-manifest.json`, and the Android `// x-release-please-version` annotation are deleted, and `git log` keeps them if the bot is ever wanted back. `version.txt` remains the source of truth and `tools/release/check-tag-version.sh` still refuses a tag that disagrees with any of the four files.
- **Alternatives**:
  - Keep release-please and give it a user-attributed token (a PAT or GitHub App installation token) so its `pull_request` events are not suppressed and its release PR can receive the required check: this is what D10 prescribed and it does work, so it was the real contender, not a strawman. Rejected because it reintroduces exactly the dependency D12 removed — a long-lived credential whose failure mode is invisible from the repository — in order to save one command. The bump is mechanical, the version choice is human either way, and `bump-version.py` is what the bot actually contributed once the changelog generation is moved into it.
  - Keep release-please but merge its PR with an admin bypass: rejected — D10 refused it and it stays refused; an always-taken bypass is not a gate.
  - Keep release-please with `skip-github-pull-request` and `skip-github-release` both set: rejected — that is a workflow that does nothing, occupying a schedule and a cache for no effect.
  - Hand-edit the four version files with no script: rejected — three formats, one of them JSON5, and a missed file is invisible until the tag guard rejects it; the guard makes it loud, but a script that cannot miss a file is better than a guard that catches the miss.
  - Have `bump-version.py` compute and apply the version without being told: rejected — the conventional-commit derivation is a good hint and a bad authority; the release number is the one part of this a person should own, so the script suggests and a human decides.

## D15 — The client-bundle record is environment-bound, and the build never renews it

- **Decision**: `presentation/official-web/client-bundles` keeps ONE committed record — `MANIFEST.sha256`, the reference build's — and the recipe writes its own to `MANIFEST.sha256.computed` beside the (untracked, cached) tree without touching the committed one. `verify-manifest.mjs` compares the two and bounds the divergence: a file whose digest differs is accepted only if its bytes embed the work directory (as the path given or with any leading directory prefix), which is the class the upstream build creates by embedding its absolute work path in the `dsh-css` region markers and in lightningcss's css-module `[hash]_[local]`, and which is exactly the 40-of-116 files the Linux CI build reports against a macOS reference record (measured). Any divergence OUTSIDE that class fails loud. Verification answers two questions with the two records: the tree is verified against the record that travels with it (what this environment built — the integrity question a cache restore can answer anywhere, and the one `ensure-client-bundles.sh` and `runtime/spike/ci/web-plugins-payload.mjs` ask), while the committed record is compared on every run and its divergence reported by count and class. A macOS↔Linux byte-identical record is not achievable while upstream's build embeds the path — the class-name hash cannot be normalised after the fact — so the record does not claim it. Re-recording the reference is a deliberate act after a reviewed diff, and `PROVENANCE.md` carries the recipe.
- **Alternatives**:
  - Patch upstream's css-module build to hash a path-independent filename, so byte-identical records become possible across environments: rejected. It is the only route to true cross-platform reproducibility, but it means vendoring a MODIFIED upstream build (D6's "never vendor modified copies" discipline, and PROVENANCE's "no upstream file was modified") and regenerating all 116 staged files plus the on-device evidence that the official-web boot legs rest on — a product change wearing a build-script costume.
  - Commit the Linux CI build's record instead, making the pipeline the reference environment: rejected. It only moves the divergence to the developer's machine, it silently re-arms on any runner-image change (node major, Ubuntu base), and it would make the record verify exactly one environment — the one that never needed help.
  - Keep regenerating the committed record and verify the rebuilt tree against a manifest the same run just wrote (the previous recipe): rejected — that is self-certification, it cannot detect non-reproducibility, and it churned the cache key so the official-web cache never hit (the 230 s rebuild in `dev/android` and the larger one in `release/ios`).
  - Record per-file NORMALISED digests (path replaced by a placeholder) so any environment could verify the reference record exactly: rejected on measurement — the css-module class name is a hash OF the path, not the path itself, so normalisation cannot equalise it and the check would reject every environment, including the reference one.

## D16 — The emulated Linux userland is the execution route that makes "install and run real programs" real, and it is adopted with its licence and audit consequences named

- **Decision**: `contract/` gains v1.3.0 `ishRun` — one program in the host's **in-process emulated Linux userland** — and iOS implements it: the iSH-arm64 engine, vendored VERBATIM and sha256-pinned by `runtime/spike/vendor/ensure-ish.sh` (never modified, D6), driven by `runtime/spike/host/dsh_ish.{c,h}` (boot once; each command runs as a child of the guest's init with its own pipes and the exit status read off the guest's zombie) and mounted as the third executor on the upstream `ctx.shell` seam by `system-plugins/dsh-shell-ish`. The engine is a **userspace interpreter for both the guest's instructions and its syscalls**, so a real Alpine userland runs inside the app's own process: this does not contradict D2 — no child process, no second OS, no JIT, and the gateway still dispatches onto the runtime's serial queue; what changes is what "in-process" is spent on. Android and HarmonyOS answer `unavailable` and keep the WebAssembly shell — capability negotiation, not a platform branch. Verified by `tools/e2e/run-ish-local.sh`, which layers two gates deliberately: the C gate (boot + commands straight through the seam, no JS) and the JS gate (scenario → plugin executor → gateway `ishRun` → host backend → guest, 11/11 records matched one-to-one), plus a **deliverable** the logs cannot fake — the guest writes a file into the mounted workspace, the JS layer reads it back through the gateway and logs its digest, and the script compares that digest with the file on disk. A simulator leg boots the same guest inside an iPad app (41–79 ms) and installs a package with the guest's own `apk` mid-session. **The one consequence that needs the owner's explicit call before the first distribution containing the engine: iSH is GPL-2/3 (+`LICENSE.IOS`), so statically linking it makes the distributed work GPL-3.0 — and this repository has no LICENSE file.**
- **Alternatives**:
  - **Stay with the in-process interpreters only (QuickJS + `wasmRun`, the status quo)**: rejected as the foundation for "install real programs". The WASM seam is a pure-function ABI by construction (input string → `dsh.emit` bytes → i32; the WASI backends are deliberately outside the vendored closure), so an installed module cannot open a file, read argv, or see a clock — and the route to a real program ecosystem (a registry, a wasm toolchain, the runtimes themselves) is entirely in front of us. The guest route inherits `apk`/`pip`/`npm` as-is: measured in this repository, `git`, `python3`, `gcc`, `make`, `sqlite`, `jq`, `bash`, `curl` and Node 22 all install and run inside the guest.
  - **Real subprocesses (`dsh-bash-local` and friends)**: not available rather than not chosen — iOS permits no child process (D2, and the PR #136 survey settled it), and Android 10+ blocks `execve` of files in app data (Termux survives by pinning targetSdk 28 and leaving Play). iOS's sanctioned shapes are in-process interpreters, which is what both `wasmRun` and `ishRun` are.
  - **nodejs-mobile / V8 on the host**: refused by D1 (an order of magnitude more memory, JIT grey zones, no multi-runtime isolation) and now measured — under a legitimate iOS app V8 can only run jitless, and jitless V8 has **no WebAssembly at all** (`typeof WebAssembly === "undefined"`), which is why the upstream rootfs ships pure-JS llhttp/fetch polyfills. A heavier, slower QuickJS.
  - **Extend the WASM shell to WASI instead (the previous assessment's recommendation)**: still the right route for the other platforms and for small tools, and it remains available; rejected as *the* foundation because it requires building the registry, the toolchain and every runtime before the first real program runs, and because it cannot run the stock userland binaries the ecosystem actually ships.
  - **Ship the guest and claim per-call enforcement**: rejected outright. The guest's sockets are host BSD sockets (`fs/sock.c`) and its paths are host paths (`fs/real.c`), so `fsWrite`/`httpFetch` flags do not gate them and there is no per-call audit record for them; measured: HTTPS egress, DNS, a non-HTTP port and a POST-shaped upload all succeed unmediated, and in realfs mode a guest write appears on the host filesystem as an ordinary file. The contract therefore **requires** the host to state what §6's audit cannot reach (§7 point 2); the interposition route (routing those two translation points through the gateway) is named as the follow-up that would restore per-call enforcement, not pretended to exist.
  - **Name the primitive after the substrate (`linuxRun`/`guestRun`) rather than the engine (`ishRun`)**: considered and deferred. `wasmRun` names a format; "ish" names one engine, and a platform-neutral contract should not — but the in-flight implementation and its E2E already spell it `ishRun` everywhere, and a mechanical rename is churn with no behaviour behind it. Recorded here so the choice is visible: if a second engine ever serves this primitive, that is the rename to make.
  - **Ship the guest userland as a plain folder inside the iOS app bundle**: rejected by measurement — `simctl install` refuses it (`invalid symlink at …/rootfs/usr/bin/top`): the Alpine tree carries 335 symlinks, many absolute (`/bin/busybox`). The userland must travel as a **fakefs image** (symlinks live in `meta.db`) or as a tar extracted into the container at first launch, which is what the reference projects do.
  - **Use the engine's own CLI as the tool's backend**: rejected — measured, the CLI returns 0 for every guest exit status (`exit 7`, `false`, a missing command all report success), and a command line ≥16 KB SIGSEGVs the host and hangs (`char argv_copy[4096]`, filed upstream as OpenMinis/ish-arm64#42). Only the embedded path (child of init + zombie wait, which is what `dsh_ish.c` uses) preserves the exit status, and it takes a 20 000-character command line without complaint.

## D17 — The build system is one facade, and the repository is layered periphery-around-project

**Decision**: `build/build.sh` is the single build entry (`build|test|check|sync` × `ios|android|harmony|core|all`, one or many platforms), where `build` means sync-closures → compile → test per platform using the exact commands the matching `dev/<platform>` CI workflow runs (BUILD.md keeps the mapping). The top level is the periphery ring — `build/` (build system), `test/` (was `tools/e2e`), `docs/`, `packages/` (was `tools/release`), `tools/` (govrail checkers only) — around the project itself: the shared core (`contract/`, `runtime/`, `system-plugins/`, `presentation/` — one copy, the DSH method per D6/D9) plus the three platform hosts under `hosts/`. The `closures` gate (wired via `gov gate add`, run by `build/check-closures.sh`) makes every committed host copy of the canonical `runtime/spike` closure a failing-able claim: the android/harmony stagers verify in `--check` mode (no writes), iOS by deterministic regen + git-diff. Old paths map: `tools/e2e → test/e2e`, `tools/release → packages/release` (historical notes and receipts keep their original paths — they are records, not drift).

**Alternatives**: CI calling the facade directly (deferred — commands are verbatim mirrors today; a pilot rewiring lands separately); deleting the committed host copies in favor of build-time generation (rejected — the copies are deliberate for self-contained APK/HAP and platform IDEs; the gate keeps them honest instead); a Makefile/justfile (rejected — a new tool dependency for zero expressive gain over POSIX sh); leaving the e2e/release tooling under `tools/` (rejected — the outer ring would stay unstated in the tree, which was the owner's original complaint).
